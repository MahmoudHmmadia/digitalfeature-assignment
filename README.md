# FeedbackHub

FeedbackHub is an internal product feedback board. Employees can submit,
discover, vote on, and discuss product requests; administrators can triage
feedback, manage users and categories, and control application maintenance
mode.

The solution is a TypeScript monorepo with an Angular client, an Express API,
and MongoDB through Prisma. It is intentionally a modular monolith: the product
does not need the operational cost of microservices, while the route,
controller, validation, and page/service boundaries keep features independent.

## Architecture and technology

| Area         | Choice                                                     | Notes                                                                                |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Frontend     | Angular 20, standalone components, signals, reactive forms | The project pins a modern, supported Angular toolchain instead of legacy NgModules.  |
| Server state | TanStack Angular Query plus typed services                 | API calls and mutation behavior are kept outside presentation components.            |
| UI           | Tailwind CSS 4, reusable standalone UI components          | Includes shared form controls, dialogs, pagination, filters, and searchable selects. |
| Backend      | Express, TypeScript, Joi                                   | A modular monolith built on an existing, familiar backend automation structure.      |
| Data         | Prisma 6 and MongoDB 7                                     | Counts are derived from vote and comment records.                                    |
| API contract | OpenAPI 3.0 and Swagger UI                                 | Generated by the server at runtime.                                                  |
| Workspace    | Bun 1.3.5 and Turborepo                                    | Runs and builds the client and server from one repository.                           |
| Deployment   | Multi-stage Dockerfiles, Compose, Kubernetes               | Environment-driven configuration with health probes and persistent data.             |

```text
Browser
  -> Angular static application served by Nginx
  -> /api proxy
  -> Express API (auth, accounts, feedback, votes, comments, categories, admin)
  -> Prisma
  -> MongoDB replica set
```

## Prerequisites

- Bun 1.3.5 or newer
- A Node.js version supported by Angular 20
- Docker with Compose for the local MongoDB or the complete container stack

## Local setup

Install workspace dependencies:

```bash
bun install
```

Copy `server/.env.example` to `server/.env` and replace at least `SECRET`.
Start the MongoDB replica set, generate Prisma Client, sync the schema, and seed
demonstration data:

```bash
docker compose up -d mongodb
bun run db:generate
bun run db:push
bun run db:seed
```

The seed is idempotent and creates an administrator, normal users, categories,
enough feedback for pagination, votes, and comments. Credentials come from the
`ADMIN_*` variables; seeded normal users use the documented development password
`user123456`.

Run both applications:

```bash
bun run dev
```

Or run them separately:

```bash
bun run dev:server
bun run dev:client
```

Local endpoints:

- Angular: `http://localhost:4200`
- API: `http://localhost:3000/api`
- Health: `http://localhost:3000/health`
- Swagger UI: `http://localhost:3000/api-docs`
- OpenAPI JSON: `http://localhost:3000/api-docs.json`

Angular's development proxy forwards `/api` and `/assets` to port 3000. This is
the same URL shape used by the Nginx deployment, so no environment-specific API
address is compiled into the client.

## Environment variables

The complete local template is in `server/.env.example`; the Compose template is
in `.env.example`.

| Variable                                      | Required              | Purpose                                                                                              |
| --------------------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------- |
| `PORT`                                        | Yes                   | Express listen port.                                                                                 |
| `DATABASE_URL`                                | Yes                   | MongoDB connection string. Use `mongodb` as the host inside Compose.                                 |
| `SECRET`                                      | Yes                   | JWT signing secret; use a long random value.                                                         |
| `MODE`                                        | Yes                   | `DEV` uses the fixed OTP `000000`; other values send email.                                          |
| `DEV_URL` / `URL`                             | Yes                   | Base URL used when producing uploaded asset links.                                                   |
| `IMAGES_PATH` / `ASSETS_PATH`                 | Yes                   | Public asset path segments.                                                                          |
| `EMAIL`, `PASSWORD`, `EMAIL_FORM`             | Production email only | Gmail SMTP credentials and sender address. `EMAIL_FORM` preserves the existing code's variable name. |
| `ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD` | Seed only             | Demonstration administrator credentials.                                                             |
| `PRISMA_DB_PUSH`                              | Containers only       | Controls automatic schema synchronization in the API entrypoint.                                     |

Never commit `.env` files or real credentials.

## Docker Compose

To run the complete stack:

```bash
cp .env.example .env
docker compose up --build
docker compose exec server bun --cwd /app/server run db:seed
```

Open `http://localhost:8080`. See `deploy/README.md` for Compose operation,
Kubernetes deployment, image tagging, and production-hardening notes.

## Build, tests, and verification

```bash
bun --cwd server run typecheck
bun run build:server
bun run build:client
```

The repository currently has no automated test suite; the `test` scripts are
placeholders and this is an explicit scope limitation. Important manual checks
are:

1. Register, verify with `000000` in `DEV`, log in, and reset the password.
2. Create, edit, and delete owned feedback; verify another user cannot modify it.
3. Search, filter, sort, and paginate feedback.
4. Vote/unvote and add, edit, and delete comments.
5. Log in as an admin to pin requests, change status, manage users/categories,
   and toggle maintenance mode.
6. Open `/api-docs`, authorize with a bearer token, and exercise protected APIs.

## Implemented

- Email/password authentication with OTP verification, password reset, JWT
  sessions, route guards, and server-side role checks.
- Feedback create/read/update/delete, ownership checks, search, category/status
  filtering, sorting, pagination, derived counts, and pinning/status triage.
- Vote toggle and vote history; comment creation, editing, deletion, and admin
  moderation at the API level.
- Profile/avatar editing, account deletion, admin user suspension/deletion, and
  admin analytics.
- Category administration and maintenance-mode settings.
- English/Arabic interface strings, responsive layouts, reusable UI controls,
  and loading, empty, and error states across the main workflows.
- Demonstration seed data, complete Swagger/OpenAPI documentation, and deployment
  artifacts.

## Known limitations

- The assignment requests an open-source identity provider and a social login.
  This implementation still uses custom JWT/email-password/OTP authentication.
- Workflow statuses are integer values rather than an admin-configurable entity.
- Registration policies, comment approval, configurable rate limits, and the
  complete notification/preferences model are not implemented. Submission
  limiting is currently fixed at ten feedback requests per 24 hours.
- The vote controller prevents duplicates through an application check, but the
  database schema does not yet enforce the required compound unique constraint.
- Several secondary admin routes are explanatory placeholder pages; the working
  category controls are part of the admin settings page.
- There are no automated tests. Kubernetes manifests are a local/orchestrator
  baseline, not a production MongoDB or ingress/security configuration.
